# 项目收口与缺口修复计划（2026-06-10）

## 一、计划目标

本计划用于解决当前项目“主流程已基本成型，但仍存在关键链路未闭环、旧链路未彻底收口、部分模块仍处于演示态/占位态”的问题。

目标分为 4 类：

1. 先确认当前分支可编译、可测试、可构建、关键接口不炸。
2. 优先补齐支付、退款、登录认证这类高风险主链路。
3. 再补齐数据分析、财务流水、门店/POS 这类业务闭环能力。
4. 最后处理 AI、工程化与旧模块去留。

## 三、GPT 报告遗漏的缺口（Claude 新发现）

### 缺口 G1：`retry_task` 表无 Java 代码（已修复）

- **问题**：`payment-system/sql/19_message_retry.sql` 定义了 `retry_task` 表和 `message_consume_log` 表，但项目中无对应 Entity 和 Mapper
- **影响**：重试任务无法通过 Java 代码管理，消息治理链路不完整
- **修复状态**：✅ 已补充
  - `RetryTask.java`（Entity）
  - `RetryTaskMapper.java`（Mapper）
  - `MessageConsumeLog.java`（Entity）
  - `MessageConsumeLogMapper.java`（Mapper）

### 缺口 G2：通知系统只能读不能发（已修复）

- **问题**：`UserNotificationService` 仅有 `list()` 和 `markRead()`，无任何发送/创建通知的能力。业务模块（订单完成、退款、优惠券等）无法向用户推送通知
- **影响**：通知表存在但无法被业务代码写入，功能闭环断裂
- **修复状态**：✅ 已补充
  - `UserNotificationService` 新增 `send(platformUserId, title, content, category)` 方法
  - `UserNotificationServiceImpl` 实现通知创建逻辑

### 缺口 G3：OrderConsumer 有 2 个 TODO（确认）

- **问题**：`OrderConsumer.java:173,177` 有两处 TODO，库存扣减和优惠券核销被推迟到 SalesOrder 流程
- **影响**：旧支付链路的库存和优惠券处理不完整，但 V1 链路（`PaymentV1Consumer`）已完整实现
- **建议**：随旧支付链路（P0-2）一并清理

### 缺口 G4：MQ 补偿任务无管理接口（确认）

- **问题**：`CompensationTask` Entity 和 Mapper 存在，但无 `CompensationTaskService` / `CompensationTaskController`，运维无法查询、重试或管理补偿任务
- **影响**：补偿任务只能通过 `RefundTaskScheduler` 自动调度，无法人工干预
- **建议**：在阶段 1 补齐管理接口

## 五、总体执行顺序

建议按以下顺序推进：

1. 质量闸门与基线确认
2. 支付与退款链路收口（含 G3 OrderConsumer TODO 清理）
3. 登录认证真实化

8. AI 助手真实联调

这样排的原因很简单：

- 先修资金和认证，避免“能演示但不敢上线”
- 再做分析和财务，补业务闭环
- 再做门店/POS/AI 这些扩展能力
- 最后做通用工程化整理

## 阶段 1：支付与退款链路收口

### 目标

让资金主链路达到“可上线审查”的程度。

### 要做什么

#### 1. 清理旧支付路径

处理对象：

- `PaymentServiceImpl`
- `PaymentOrderServiceImpl`
- `OrderConsumer`
- 相关旧支付入口

建议做法：

1. 先全局搜索哪些入口还在被调用。
2. 若完全无用：
   - 删除旧入口
   - 删除旧 service/consumer
3. 若短期还要保留：
   - 明确 `@Deprecated`
   - 加 `dev/test` profile 限制
   - 在文档中声明不再用于生产链路

#### 2. 补齐支付宝订单查询

建议做法：

1. 在旧支付链路若保留，则补真实 `AlipayTradeQueryRequest`。
2. 若旧支付链路决定废弃，则直接删除 `queryAlipayOrder` 相关逻辑，不留假实现。

#### 3. 补齐退款渠道真实调用

建议做法：

1. 为 `PaymentProvider` 的支付宝/微信实现补 `refund(...)` 与 `queryRefund(...)`。
2. 衔接 `RefundServiceImpl` 中：
   - 提交退款
   - 查询退款
   - 回调/补偿结果更新
3. 明确状态机：
   - APPLIED
   - PROCESSING
   - SUCCESS
   - FAIL
4. 验证补偿任务和对账任务是否按预期推进。

#### 4. 退役验签桩

建议做法：

1. 若生产已不需要，直接删除 `PaymentSignatureVerifierStub`。
2. 若保留用于开发联调：
   - 限定 `@Profile("dev")`
   - 保证 fail-closed
   - 在主配置中避免生产注入

### 验收标准

- 旧支付链路明确退役或受限
- 退款链路至少 1 个真实渠道可跑通
- 支付/退款相关单测和关键集成测试通过
- 不再存在“TODO/phase 1 not supported”挂在主路径上
