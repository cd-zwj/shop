# 多租户SaaS系统 — 项目架构全景文档

> 最后更新：2026-06-07
> 分支：codex-dual-wallet-v1

---

## 一、项目概述

**定位**：多租户商户SaaS平台，支持C端用户消费、B端商户运营管理、Admin端平台治理。

**技术栈**：

| 层 | 技术 |
|---|------|
| 后端 | Spring Boot + MyBatis-Plus + Sa-Token + RabbitMQ |
| 前端 | React + TypeScript + Vite + Tailwind CSS |
| 数据库 | MySQL 8 (payment_db) + Redis + Elasticsearch |
| 对象存储 | MinIO |
| 支付 | 微信支付V3 + 支付宝 + 第三方扩展 |
| AI | LangChain4j + 通义千问 |
| 消息队列 | RabbitMQ（手动ACK + 重试 + 死信） |

**多租户策略**：行级隔离——业务表含 `tenant_id`，MyBatis-Plus 租户拦截器自动注入。

## 五、数据库结构合理性分析

### ✅ 设计良好的部分

**1. 租户隔离**：几乎所有业务表含 `tenant_id`，配合 MyBatis-Plus 租户拦截器，实现行级隔离，正确。

**2. 双钱包架构**：`unified_wallet_account`（用户级）+ `merchant_wallet_account`（商户级）分离，支持混合支付策略，设计合理。

**3. 乐观锁**：`product_stock.version`、`user_coupon.version`、`unified_wallet_account.version` 等使用版本号防并发，正确。

**4. 消息可靠性**：Outbox + 幂等 + 补偿 + 死信，完整链路，企业级设计。

**5. 优惠券生命周期**：模板→领取→锁定→核销→释放→过期，全链路有对应表和记录，非常完整。

**6. 退款双层设计**：`refund_application`（用户申请层）与 `refund_order`（支付渠道执行层）分离，职责清晰。

**7. RBAC权限**：5表标准RBAC模型（用户-角色-权限），支持用户级额外权限覆盖。

---

### ⚠️ 需要关注的问题

#### 问题1：新旧模型并存（高优先级）

**现状**：`sys_user`（旧）和 `platform_user`（V1）两套用户表并存。

| 维度 | 旧版 | V1新版 |
|------|------|--------|
| 用户表 | sys_user | platform_user |
| 订单表 | payment_order | sales_order |
| 钱包表 | user_balance | unified_wallet_account |
| 积分表 | user_points | member_points_account |
| 充值表 | recharge_rule | merchant_recharge_rule |

**风险**：
- 旧版 Controller（UserController, AdminController, MiniProgramController）仍在使用旧表
- 旧表和新表数据可能不一致
- 新用户只写 platform_user，旧表无数据

**建议**：
- 制定旧版下线计划，确定哪些旧 Controller 仍在生产使用
- 对不再使用的旧 Controller 加 `@Deprecated` + `@Profile("!prod")`
- 旧表保留但标记为 deprecated，新功能只用新表

#### 问题2：缺少外键约束（中优先级）

**现状**：所有表关系通过应用层维护，数据库层面无外键约束。

**影响**：
- 数据孤立风险：删除 coupon_template 后 user_coupon 引用的 template_id 变成孤儿
- 开发调试困难：无法通过数据库直接看到表间关系

**建议**：
- 至少在关键关系上添加外键注释文档（不一定要物理外键，但要有 ER 图说明）
- 应用层校验：确保删除前检查引用

#### 问题3：部分表缺少索引（中优先级）

需要确认的索引：

| 表 | 查询模式 | 需要的索引 |
|---|---|---|
| sales_order | 按 user + status 查询 | (platform_user_id, order_status) |
| sales_order | 按 tenant + status 查询 | (tenant_id, order_status) |
| user_coupon | 按 user + status 查询 | (platform_user_id, coupon_status) |
| payment_bill | 按 bill_no 查询 | (bill_no) 唯一索引 |
| unified_wallet_log | 按 user + 时间查询 | (platform_user_id, create_time) |
| refund_application | 按 order_no 查询 | (order_no) |
| login_fail_record | 按 account 查询 | (account) |

#### 问题4：金额字段类型不统一（中优先级）

| 层 | 类型 | 说明 |
|---|---|---|
| 数据库 | DECIMAL(12,2) | 元 |
| Entity | BigDecimal | 元 |
| VO | Long | 分（×100转换） |
| 前端 | number | 分（从VO接收） |

**风险**：VO 转换层是新增的，部分旧 Controller 仍直接返回 Entity（BigDecimal），前端可能混用两种单位。

**建议**：统一确认所有 V1 接口已走 VO 转换，旧接口逐步迁移。

#### 问题5：数据量增长风险（低优先级）

| 表 | 增长速度 | 风险 |
|---|---|---|
| payment_callback_record | 每笔支付1-3条 | 高 |
| user_behavior_log | 每次操作1条 | 高 |
| points_log / balance_log / wallet_log | 每次变动1条 | 中 |
| message_consume_log | 每条消息1条 | 中 |
| coupon_receive_record / write_off_record | 每次操作1条 | 中 |

**建议**：
- 设计归档策略：超过6个月的日志表迁移到归档库
- 考虑分区表：按月分区 `payment_callback_record`、`user_behavior_log`
- 定期清理：`message_consume_log`、`dead_letter_task` 超过30天的记录清理

#### 问题6：`Store` 表未充分利用（低优先级）

`store` 表已存在但前后端仍围绕 `tenant` 级别操作。如果后续要做门店级管理（多门店商户），需要：
- 商品表增加 `store_id` 字段
- 订单表增加 `store_id` 字段
- 前端增加门店选择器
