## 2. #27 数据看板可视化计划

### 2.1 范围

本轮做“管理端经营可视化看板”，不做 AI 自动分析，不依赖旧 `/api/admin/dashboard/*` 假数据路径。

核心能力：

1. KPI 总览：复用已有 `/v1/admin/dashboard/overview`。
2. 销售趋势：按日/月统计订单金额、订单数、支付金额。
3. 用户/商户增长趋势：平台用户、商户新增趋势。
4. 商品/商户排行：销售额、订单数排行。
5. 支付/充值分布：支付渠道、充值金额趋势。

### 2.2 后端设计

优先复用现有 V1 后台聚合：

- `payment-system/src/main/java/com/payment/controller/V1AdminDashboardController.java`
- `payment-system/src/main/java/com/payment/service/V1AdminService.java`
- `payment-system/src/main/java/com/payment/service/impl/V1AdminServiceImpl.java`
- `payment-system/src/main/java/com/payment/dto/AdminDashboardOverviewVO.java`

现状约束：

- 当前 `getDashboardOverview()` 会把 `SalesOrder`、`PaymentBill`、`RechargeOrderV1` 全量 `selectList` 到 Java 内存后聚合。新增趋势、排行、分布时不能继续沿用该方式，应新增 Mapper 聚合 SQL；如改动范围允许，顺手把 overview 的大表统计也下沉到 SQL。
- 聚合口径必须只统计 `deleted=0`，金额类指标按业务状态过滤：订单以 `pay_status=SUCCESS` 为主，支付单以 `pay_status=SUCCESS` 为主，充值以 `biz_status=SUCCESS` 为主。
- 日期参数必须有默认范围和上限，默认最近 30 天，最大不超过 180 天，避免管理端无意触发大范围扫描。

新增建议接口：

```text
GET /v1/admin/dashboard/visualization?startDate=&endDate=&granularity=DAY|MONTH
```

返回一个组合 VO，避免前端多次请求：

- `overview`
- `salesTrend`
- `merchantTrend`
- `userTrend`
- `productRank`
- `paymentChannelDistribution`
- `rechargeTrend`

新增/调整文件：

- `dto/AdminDashboardVisualizationVO.java`
- `dto/AdminDashboardTrendPointVO.java`
- `dto/AdminDashboardRankItemVO.java`
- `dto/AdminDashboardDistributionItemVO.java`
- 相关 Mapper 聚合方法：优先使用 `SalesOrder`、`SalesOrderItem`、`PaymentBill`、`RechargeOrderV1`、`Tenant`、`PlatformUser`，避免继续依赖废弃 `PaymentOrder`。
- 建议优先补充专用聚合方法，而不是在 Service 中拼装大量 LambdaQueryWrapper 后内存处理：
  - `SalesOrderMapper.selectSalesTrend(...)`
  - `SalesOrderMapper.selectMerchantSalesRank(...)`
  - `SalesOrderItemMapper.selectProductSalesRank(...)`
  - `PaymentBillMapper.selectChannelDistribution(...)`
  - `RechargeOrderV1Mapper.selectRechargeTrend(...)`
  - `TenantMapper.selectMerchantCreateTrend(...)`
  - `PlatformUserMapper.selectUserCreateTrend(...)`

### 2.3 前端设计

关键文件：

- `salessystem/src/pages/AdminAnalytics.tsx`
- `salessystem/src/services/modules/adminDashboard.ts`（若已有则扩展，否则新增）
- `salessystem/src/types/adminDashboard.ts`（若已有则扩展，否则新增）

原则：

- 项目已经引入并使用 Recharts，不再新增图表库。
- 当前 `AdminAnalytics.tsx` 的 `deriveTrend()` 是基于 overview 合成的 7 点假趋势，本轮必须替换为真实 `/v1/admin/dashboard/visualization` 返回数据。
- 当前页面还调用 `/analysis/list` 做异常记录分布；本轮若无真实异常分析需求，应降级为非核心模块，避免把数据看板依赖在旧分析接口上。
- 页面保持“总览卡片 + 趋势图 + 排行榜 + 分布图”的结构。
- 加时间范围筛选：最近 7 天、30 天、90 天、自定义。
- 空数据用现有 `EmptyState`，失败用 Toast/错误提示，不静默失败。

## 3. #25 门店管理计划

### 3.1 范围假设

本轮只做“门店主数据管理 MVP”，不改库存真相源，不把商品/订单强制绑定门店。

默认规则：

- 一个商户可有多个门店。
- 门店软删除。
- 状态先只做启用/停用。
- 门店编号后端生成，保持全局唯一。
- `rating` 暂作为平台/系统维护字段，后续再接用户评价聚合。
- 商户端页面不能让用户手填或猜测 `tenantId`。前端应从当前商户会话/已授权商户上下文中取 `tenantId`；后端仍以 `requireEmployee(tenantId, currentPlatformUserId)` 作为最终权限判断。

### 3.3 搜索侧修复

当前 `AppCatalogSearchServiceImpl` 已有门店筛选参数，但 `TenantMapper.selectSearchTenantPage` 疑似没有真正 JOIN `store` 表。

本轮补齐：

- 评分过滤：`store.rating`
- 距离排序/筛选：经纬度存在时计算距离。
- 多门店商户返回策略：默认返回“匹配门店中距离最近/评分最高的一条门店信息”，仍保留商户卡片语义。
- 停用或软删除门店不得参与公开搜索：`store.status=1 AND store.deleted=0`。
- 如果商户有多个匹配门店，SQL 应避免把同一商户重复分页返回；优先用子查询/窗口函数先选中每个商户的最佳门店，再和 `tenant` 聚合分页。

## 4. #24 MQ 补偿计划

### 4.1 范围

本轮做异步链路可靠性补强，不重写所有 MQ 业务。

优先覆盖：

- 支付成功业务消息：`payment.v1.order.paid`、`payment.v1.recharge.success`
- 商品索引消息：`payment.product.index`
- 扫码消息：`payment.scan.request/result`
- 已有 outbox：`message_outbox`
- 已有死信：`dead_letter_task`

### 4.2 后端设计

已有文件：

- `config/RabbitMQConfig.java`
- `entity/MessageOutbox.java`
- `mapper/MessageOutboxMapper.java`
- `entity/DeadLetterTask.java`
- `mapper/DeadLetterTaskMapper.java`
- `consumer/DeadLetterConsumer.java`
- `service/impl/PaymentBillV1ServiceImpl.java`
- `consumer/PaymentV1Consumer.java`
- `consumer/ProductIndexConsumer.java`
- `consumer/ScanConsumer.java`

新增/调整：

1. **Outbox 重试调度器**
   - `MessageOutboxRetryScheduler`
   - 扫描 `PENDING/FAIL` 且到达 `nextRetryTime` 的 outbox。
   - 成功标记 `SENT`。
   - 失败递增 `retryCount`，指数退避。
   - 超过最大次数标记 `DEAD` 并写入补偿/死信记录。

2. **死信持久化**
   - `DeadLetterConsumer` 不再只 log。
   - 将 exchange、queue、routingKey、messageId、payload、error headers 写入 `dead_letter_task`。
   - 当前 `DeadLetterConsumer` 同时承担“充值订单延迟超时处理”和通用死信日志记录；本轮改造时要保留充值超时逻辑，但把通用死信持久化抽成独立方法，避免死信落库失败影响充值超时订单取消。
   - 死信落库失败时不能静默吞掉，至少要保留错误日志和可观测告警；是否 ack 需要按“避免 DLQ 堆积”和“避免丢失死信记录”的取舍写入测试说明。

3. **队列 DLX 补齐**
   - 给 V1、product、scan 队列统一配置 dead-letter exchange。
   - 保留已有延迟队列特殊逻辑。
   - 现有带 DLX 的只有充值延迟队列、旧订单创建/支付队列；`payment.v1.recharge.success`、`payment.v1.order.paid`、`payment.product.index`、`payment.scan.request/result` 当前都需要补齐 DLX 参数。

4. **消费者失败路径收口**
   - `ProductIndexConsumer` 不再吞异常。
   - 需要重试/死信的异常要抛出或 nack。
   - 业务可忽略的异常必须显式记录原因，不能静默。

5. **幂等一致性**
   - 修复/明确 `MessageIdempotentService` 的 `(messageId, queueName)` 语义。
   - V1 消费继续保留业务状态幂等，同时增加必要日志。
   - 当前 `MessageIdempotentServiceImpl.isProcessed(messageId, queueName)` 实际只按 `messageId` 查询，没有使用 `queueName`；如果同一个 `messageId` 出现在不同队列，会误判为已消费。本轮必须修正查询条件和唯一约束语义。

### 4.3 SQL/迁移

优先复用已有：

- `payment-system/sql/19_message_retry.sql`
- `payment-system/sql/14_platform_wallet_v1.sql`

如现有表缺字段，新增迁移，不直接改历史脚本。

可能新增：

- outbox 状态索引：`send_status + next_retry_time`
- dead letter 状态索引：`handle_status + create_time`
- consume log 唯一键：`message_id + queue_name`
- `dead_letter_task` 当前只有 `message_id`、`queue_name`、`message_body`、`fail_reason`、`create_time`，不足以支撑人工处理和重放。本轮应新增迁移补齐：
  - `exchange_name`
  - `routing_key`
  - `headers_json`
  - `handle_status`
  - `retry_count`
  - `last_handle_time`
  - `update_time`
- `message_consume_log` 当前只有普通索引，没有 `(message_id, queue_name)` 唯一键；如果把它作为幂等依据，需要新增唯一约束或明确继续使用 `message_idempotent`。

### 4.4 测试与验收

新增/补充：

- `MessageOutboxRetrySchedulerTest`
- `DeadLetterConsumerTest`
- `PaymentV1ConsumerTest`
- `ProductIndexConsumerTest`
- `MessageIdempotentServiceImplTest`

手动/集成验证：

1. 人工插入一条 `message_outbox.PENDING`，调度器能发布并标记 `SENT`。
2. RabbitMQ 不可用时，重试次数递增，`nextRetryTime` 后移。
3. 超过最大重试次数后进入 `DEAD` 或死信记录。
4. 消费异常能进入 DLX，并写入 `dead_letter_task`。
5. 重复消息不会造成重复加积分、重复扣库存、重复更新订单。
6. 同一个 `messageId` 投递到不同 `queueName` 时，幂等判断不互相污染。
7. `ProductIndexConsumer` 处理异常时不会吞异常导致消息被错误 ack。
