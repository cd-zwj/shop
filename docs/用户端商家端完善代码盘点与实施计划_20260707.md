# 用户端与商家端完善代码盘点与实施计划

日期：2026-07-07

## 本次代码盘点结论

本次在动手前已阅读当前后端 `payment-system` 与前端 `salessystem` 的核心链路代码，重点覆盖用户端订单、支付、退款、购物车/结算、商品详情、资产、通知、地址/交付，以及商家端订单、退款、商品、库存、财务和待办中心。

## 仍需完善的重点缺口

### P0：后端状态展示契约后端化

现在前端 `orderLifecycle/refundProgress/paymentStatus` 已经做了大量状态说明，但订单列表接口只返回订单本体。为了拿支付单状态、交付状态、退款状态，前端 `UserOrders` 需要逐单拉详情和按商户拉退款列表。

处理方向：

- 后端订单列表和详情 VO 增加展示字段：
  - `statusLabel`
  - `statusDescription`
  - `nextStep`
  - `failureReason`
  - `availableActions`
- 后端退款 VO 增加同类展示字段：
  - `statusLabel`
  - `statusDescription`
  - `nextStep`
  - `failureReason`
  - `availableActions`
- 前端优先使用后端字段，缺失时保留现有本地推导作为兼容兜底。

### P0：钱包资金更新一致性

`UnifiedWalletServiceImpl` 当前仍采用“读取实体 -> 修改实体 -> updateById -> 重试”的写法。此前商户余额已改为条件原子更新，统一钱包和商户钱包也应按同样标准治理。

处理方向：

- 统一钱包 `credit/debit` 改为条件 SQL 更新，重试时重新读取干净账户。
- 商户钱包做同类复核和修复。
- 补并发重试单测，避免重复入账或重复扣款。

### P1：购物车结算失败可恢复体验

后端已能返回价格变化、库存不足、商品下架错误，但前端购物车需要更明确地把错误转成“刷新购物车/移除失效商品/重新选择优惠券”的动作。

处理方向：

- 增加结算前校验工具或接口。
- 前端捕获具体错误，显示失效商品、价格变化、库存变化，并提供刷新入口。

### P1：商品详情信息完整度

商品详情页还需要系统化展示：

- 库存状态
- 配送/发货方式
- 售后说明
- 商家信息
- 购买限制
- 虚拟商品交付说明：购买后在哪里查看卡密/兑换码/文件

### P1：商家财务对账视图

已有余额和提现基础，但还需把订单金额、退款、入账、冻结、可提现串成商家可读明细。

### P2：经营分析增强

商品销量排行、复购用户、退款率、客单价、转化漏斗可基于已有订单和行为数据逐步补。
