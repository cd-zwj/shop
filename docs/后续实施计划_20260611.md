## 阶段 3：管理端分析与商户财务闭环

### 目标

把管理端分析和商户财务从"能展示"提升到"真实可运营"。

### 子任务

#### 3.1 管理端趋势图接真实时序 API

**现状**：`AdminAnalytics.tsx` 的 `deriveTrend()` 函数用 `totalOrderAmount / 7` 合成一条线性增长曲线，"previous" 线是 current 的 70%。指标卡和异常图已用真实 API。

**要做什么**：

后端：
1. 在 `V1AdminDashboardController` 或新建 `V1AdminAnalyticsController` 中新增时序数据接口
2. 支持参数：`startDate`、`endDate`、`granularity`（DAY/WEEK/MONTH）
3. 返回：每日/每周/每月的订单金额、订单数、用户增长数
4. 数据源：`sales_order` 表按 `create_time` 分组聚合

前端：
1. `AdminAnalytics.tsx` 的 `deriveTrend()` 替换为真实 API 调用
2. 删除合成数据逻辑
3. 若后端数据为空，显示空态而非伪造趋势

**验收标准**：
- 趋势图展示真实时序数据
- 无数据时显示空态
- 指标卡和异常图保持不变（已用真实 API）

#### 3.2 商户财务页新增收支流水列表

**现状**：`MerchantFinance.tsx` 仅有余额汇总、运营规则、最近提现。页面自带蓝色提示："当前后端没有提供独立的收支流水接口"。

**要做什么**：

后端：
1. 新增 `V1MerchantFinanceController.listTransactions()` 端点
2. 支持参数：`startDate`、`endDate`、`type`（PAYMENT/REFUND/RECHARGE/WITHDRAWAL/POINTS）、`page`、`size`
3. 数据源：`unified_wallet_log` + `merchant_wallet_log` 表

前端：
1. `MerchantFinance.tsx` 新增"收支流水"区块
2. 表格展示：时间、类型、金额、关联单号、备注
3. 支持筛选（类型、时间范围）和分页
4. 保持现有余额、规则、提现概览不变

**验收标准**：
- 商户财务页能看到真实流水
- 支持按类型和时间筛选
- 分页正常

#### 3.3 旧分析接口确认退役

**现状**：
- `DataAnalysisController`：`@Deprecated` + `@Profile({"dev","test"})`
- `SalesStatisticsController`：`@Deprecated` + `@Profile({"dev","test"})`

**决策**：两个旧 Controller 已有 Profile 保护，生产环境不可访问。建议保持现状，不删除代码，仅在文档中标注为"已废弃，待 V1 迁移完成后移除"。

**验收标准**：
- 旧接口保持 `@Profile({"dev","test"})` 限制
- 文档标注已废弃

**完成记录（2026-06-12）**：
- 3.1 后端新增 `GET /v1/admin/dashboard/trend` 接口，SQL 级 GROUP BY 聚合（非内存加载），返回近 30 日每日订单量/金额；前端 `AdminAnalytics.tsx` 删除 `deriveTrend()` 合成数据，改用真实 API
- 3.2 后端新增 `GET /v1/merchant/tenants/{tenantId}/transactions` 接口，查询 `merchant_wallet_log` 表，支持 bizType/startDate/endDate 筛选和分页；前端 `MerchantFinance.tsx` 新增收支流水表格区块，替换原有"对接说明"蓝框

## 阶段 4：通知系统闭环 + MQ 补偿管理接口

### 目标

通知系统从"只能读"变为"业务可写"，MQ 补偿任务提供运维管理能力。

### 子任务

#### 4.1 通知 send() 接入业务模块

**现状**：`UserNotificationService.send()` 接口已就绪（含输入验证 + XSS 防御），但无业务模块调用。

**要做什么**：

在以下业务节点调用 `notificationService.send()`：

| 触发场景 | 调用位置 | 通知标题示例 | 分类 |
|----------|---------|------------|------|
| 订单支付成功 | `PaymentV1Consumer.handleOrderPaid()` | "订单支付成功" | ORDER |
| 退款申请提交 | `RefundApplicationServiceImpl.createApplication()` | "退款申请已提交" | REFUND |
| 退款成功/失败 | `RefundServiceImpl` 回调处理 | "退款已到账"/"退款失败" | REFUND |
| 提现审批通过/拒绝 | `WithdrawalServiceImpl.approve/reject()` | "提现审批通过" | PAYMENT |
| 优惠券即将过期 | `CouponTaskScheduler` 定时任务 | "优惠券即将过期" | COUPON |

**验收标准**：
- 通知可在关键业务节点自动创建
- 用户在通知中心能看到对应通知

**完成记录（2026-06-12）**：
- `PaymentV1Consumer.handleOrderPaid()`：注入 `UserNotificationService`，订单状态更新后发送 ORDER 类通知
- `RefundApplicationServiceImpl.createRefund()`：退款申请创建后发送 REFUND 类通知
- `RefundServiceImpl.markRefundSuccess/markRefundFailure()`：退款成功/失败后发送 REFUND 类通知，`platformUserId` 从 `RefundOrder` 取
- `WithdrawalServiceImpl.approveWithdrawal/rejectWithdrawal()`：审批后发送 PAYMENT 类通知，通过 `TenantEmployeeMapper` 查找商户首个员工的 `platformUserId`
- `CouponTaskScheduler`：因只有过期总数无 userId 粒度，暂不接入通知

#### 4.2 补齐 CompensationTaskService + Controller

**现状**：`CompensationTask` Entity + Mapper 存在，但无 Service/Controller，运维无法查询和管理补偿任务。

**要做什么**：

后端：
1. 新增 `CompensationTaskService` 接口：`list()`、`retry()`、`cancel()`
2. 新增 `CompensationTaskServiceImpl` 实现
3. 新增 `V1AdminCompensationController`：管理端查询/重试/取消补偿任务
4. 补齐 `RetryTask` 的 Service 层（当前仅有 Entity + Mapper）

**验收标准**：
- 管理端可通过 API 查询补偿任务列表
- 支持手动重试和取消
- 权限限制为管理员角色

**完成记录（2026-06-12）**：
- 新建 `CompensationTaskService` 接口 + `CompensationTaskServiceImpl`：list(status, bizType, page, size) / retry(重置 PENDING) / cancel(标记 CANCELLED)
- 新建 `RetryTaskService` 接口 + `RetryTaskServiceImpl`：list / retry(FAIL/DEAD/CANCELLED → PENDING) / cancel(PENDING → CANCELLED)
- 新建 `V1AdminCompensationController`：6 个端点（补偿任务 3 个 + 重试任务 3 个），全部需 `admin:dashboard` 权限
- 6 个新文件：2 接口 + 2 实现 + 1 Controller

## 阶段 5：门店主数据收口 + POS 下线

### 目标

明确门店和 POS 模块的去留。

### 子任务

#### 5.1 门店模块决策

**现状**：`Store` 实体和 `StoreMapper` 存在但完全孤立，无 Service/Controller，无任何代码引用。实体有丰富字段（经纬度、评分、营业时间、服务标签）。

**需要决策**：
- **方案 A**：建设多门店能力 → 新增 StoreService/StoreController，商品/订单增加 store_id
- **方案 B**：暂不做 → 保持现状，在文档中标注"数据预埋，暂不建设"

**建议**：方案 B，当前项目以单门店商户为主，多门店是后续扩展。

#### 5.2 POS 模块下线

**现状**：`PosController` 已有 `@Deprecated` + `@Profile({"dev","test"})`。

**要做什么**：
1. 确认前端无 POS 相关入口/菜单
2. 确认无其他代码引用 `PosController`（排除测试）；`ScanService` 仍被扫码链路（ScanConsumer、NettyServer）引用，本阶段不处理
3. 在文档中标注"POS 已下线，代码保留用于参考"

**验收标准**：
- 门店有明确结论
- POS 有明确结论
- 文档更新

**完成记录（2026-06-12）**：

**5.1 门店模块 — 决策：方案 B（数据预埋，暂不建设）**
- `Store.java` + `StoreMapper.java`：孤立实体，无 Service/Controller 业务代码引用
- `SalesOrder.storeId` 和 `Product.storeId` 已预留字段（27_new_modules.sql），但当前业务代码未读写，未形成门店业务闭环
- 代码标注：`Store.java` Javadoc 注明"数据预埋，暂不建设"，注明 store_id 预留情况

**5.2 POS 模块 — 确认已下线**
- `PosController.java`：`@Deprecated` + `@Profile({"dev","test"})` 双标记，生产不可用，零外部引用
- 前端零入口：App.tsx 路由表、底部导航栏、管理员/商户侧边栏均无 POS 路由/菜单
- `ScanService` 仍被 `ScanConsumer` 和 `NettyServer` 引用，属于扫码链路配套，本阶段不处理，待后续评估
- 代码标注：PosController Javadoc 注明"已下线，代码保留用于参考"

| 方案 | 工作量 | 说明 |
|------|--------|------|
| **A：真实联调** | 大 | 接入 LangChain4j + 通义千问，实现商品推荐/消费分析对话 |
